Playing Lander on the ARM Evaluation System

How I persuaded Lander to run on the ARM Evaluation System

I have long been fascinated by the early history of ARM, and being a big fan of Elite, I'm especially fond of the story of how David Braben developed Lander on the ARM Evaluation System (you can read all about it in my deep dive on Lander's origins on the ARM1).

For this hack I wanted to create an homage to David Braben's original development environment by taking the version of Lander that came with the Archimedes and persuading it to run on the ARM Evaluation System (AES). Here are the results:

This clip shows Lander running in an AES that's attached to a BBC Master via the Tube interface. This is the same interface that the 6502 Second Processor uses, which was used to such great effect by Bell and Braben with their colour version of Elite (see my Elite project for more details on this version).

To get Lander working on the AES, I decided to reuse the same approach as Elite. In this setup, the code running on the ARM side of the Tube is the original Lander, it's just been patched to transmit graphics and keyboard across the Tube rather than talking to VIDC and IOC on an Archimedes. The code running on the 6502 side of the Tube is based on the I/O processor code from the 6502 Second Processor of Elite. So this is not only an ARM/6502 mash-up, it's also a Lander/Elite mash-up, and given that David Braben wrote Lander and co-wrote Elite, it's a very pleasing combination.

The slow speed is mainly down to the bottleneck of sending graphics data over the Tube. I'm guessing that it's somewhere between a half and one-third of the speed of the game running on an ARM2; the AES is clocked more slowly than an Archimedes too, so that's another factor. It's a lot more fluid if you play it in your emulator with the speed ramped up a bit.

Modifying Lander for the AES
----------------------------

As with all my hacks, I have released the source code, fully marked up with the before-and-after changes that I've made to Lander and Elite to get this working. It's in the arm-evaluation-system branch of my Lander repository, where you can find both the AES parasite and I/O processor sources. If you want to see exactly what I have modified to get Lander working on the AES, you can search the sources for "Mod:" to see the code that I've changed.

Here's a brief summary of the main changes:

  • As the AES does not have a mouse, the OS_Mouse SWI isn't supported, so I've replaced it with two new routines called ReadKeyboardMouseButtons and GetPolarAnglesFromKeyboard. The first one reads the BBC Master keyboard for the fire and thrust keys to replicate the mouse button controls of the original, and the second on reads the pitch and yaw keys and calculates the same polar coordinates that would normally be calculated from the mouse position.
  • The AES doesn't support the OS_BinaryToDecimal SWI, so I've replaced this with a simple number-printing routine called ConvertBinaryToDecimal that's based on Elite's BPRNT algorithm.
  • All the Archimedes-specific bank-switching code is disabled and is replaced by calls to the API's Tube_SetScreenBank command (see below).
  • Colours are set to mode 1 pixel bytes (i.e. four pixels in the correct colour) rather than 32-bit VIDC colours, so the ship and bullets are magenta, trees are green, shadows are blue, buildings and destroyed objects are magenta, the landscape is green for land and blue for sea, and so on. Particles are the exception; for these, I just use the relevant pixel bits from the 32-bit VIDC colour as the pixel byte, so explosions and thrust particles end up being randomly coloured with no extra effort (the only particle that is a fixed colour is the bullet particle).
  • Each pixel is transmitted to the BBC Master as four bytes:
    • The two-byte mode 1 screen address that contains the pixel(s)
    • The mode 1 pixel byte containing the pixel(s) to draw in the relevant colour(s), where the four colours are 0 (black), 1 (magenta), 2 (green) and 3 (blue) - for an explanation of the four-pixels-per-byte structure of mode 1, see the deep dive on drawing colour pixels on the BBC Micro in my Elite project; mode 1 has the same structure as mode 5 but with a higher horizontal resolution
    • The mode 1 pixel mask that corresponds to the pixel(s) to draw, with clear bit-pairs for the pixels to draw and set pixels for the bit-pairs to preserve
    The drawing process in the BBC Master is therefore as simple as possible: we fetch the existing contents of the mode 1 screen address, AND it with the pixel mask to zero the pixel(s) we want to draw while leaving the other pixels alone, and ORA it with the pixel byte to insert the pixel(s) we want to draw into the pixel byte, which we then write back into screen memory. There are no costly calculations of the memory address or pixel mask in the I/O processor - we do all of that in the AES, using the much faster ARM processor.
  • Every time we draw a pixel by transmitting it across the Tube, the AES keeps track of the screen address range of that frame's pixel content by updating the maximum and minimum address in the maxScreenAddr and minScreenAddr variables. Once the entire screen has been drawn, these values are passed to the I/O processor via the API's Tube_SendScreenRange command, so that when the I/O processor clears the screen to draw the next frame, it only needs to clear screen memory within that address range.
  • The entire fuel bar is drawn once at the start of each game (into both screen banks), and as the game progresses, we only need to redraw the last character block (four pixels) of the bar plus the block to the right of the bar, and then the bar will grow or shrink cleanly with only two bytes (eight pixels) of screen-writing.
  • The memory test in the Entry routine is disabled, as it isn't needed.

There are few other minor changes. For example, the ARM code in the AES runs at address &1000 rather than the &8000 of the Archimedes, and I've zeroed the value of the screenAddr variable so that screen address calculations within the Lander code will give results as offsets from the start of the screen rather than Archimedes screen addresses. But overall the changes to Lander are minimal, and are mainly concerned with drawing the screen via the Tube and replacing the mouse with a keyboard.

Indeed, it's a pixel-perfect version of Lander too, as both mode 1 (on the BBC) and mode 13 (on the Archimedes) are 320 by 256 pixels; the obvious difference is that the BBC only has four colours while the Archimedes has 256, but the identical resolution means that Lander on the AES and Lander on the Archimedes match precisely in terms of pixel location. Of course, the Archimedes version has filled square tiles rather than corner dots, but the screen coordinates of those corners match perfectly and the game works in exactly the same way.

In other words, this is Lander, it's just on the AES.

The Tube API for Lander
-----------------------

For an explanation of how the Tube API works in Elite, see the deep dive on 6502 Second Processor Tube communication in my Elite project. Lander works in exactly the same way and reuses quite a bit of code from Elite, except the Lander API contains a set of commands that are modified to the requirements of Lander.

In the following tables, routines with all-capital names are taken from Elite and modified for use in Lander, while routines in camel case are brand new code for Lander. See the I/O processor source to see how these commands are implemented on the BBC Master side of the Tube.

Here are the OSBYTE commands:

OffsetVariableOSWRCH #ActionI/O routine
0-128 (&80)Put back to USOSWRCHUSOSWRCH
1-129 (&81)Reserved for VDU code for mode 128+1USOSWRCH
2#Tube_AddPixels130 (&82)Receive a pixel to drawADDBYT
3#Tube_BeginPixels131 (&83)Start receiving pixelsBEGINLIN
4#Tube_SetScreenBank132 (&84)Set screen bank to main or shadowSetScreenBank
5#Tube_ClearScreen133 (&85)Switch screen bank and clear screenClearScreen
6#Tube_SetScreenMode134 (&86)Set up the game's screen modeSetScreenMode

As with Elite, OSWRCH commands enjoy a degree of parallelism, so when sending batches of pixels to the AES with the BEGINLIN and ADDBYT commands, the last pixel will start the BBC Master drawing those pixels while the Lander code in the AES can continue processing in parallel.

Command 129 is reserved for changing the mode to mode 1 with shadow RAM enabled, which is done by writing ASCII 2 followed by the mode number 129. We reserve 129 for the mode number because otherwise the custom OSWRCH handler would interfere with the mode change.

Here are the OSWORD commands:

OffsetVariableOSWORD #ActionI/O routine
0#Tube_ReadKeyboard240 (&F0)Scan the keyboard for game keysKEYBOARD
1#Tube_SendScreenRange241 (&F1)Set max/min screen addressesSetScreenRange
2#Tube_ScanKeyboard242 (&F2)Scan the keyboard for any keyScanKeyboard

Calling these commands will block the AES caller until the results are returned, just as with Elite. This works well for the keyboard commands, and it doesn't matter if we block for the Tube_SendScreenRange command as it is only called once for each frame, when switching screen bank (for the latter, using OSWORD is simply more convenient that OSBYTE for sending the four bytes of data in the maximum and minimum screen addresses).

So that's how Lander works on the ARM Evaluation System, by using Elite's co-processor API to process graphics and keyboard on the BBC Master while the ARM1 runs Lander.
